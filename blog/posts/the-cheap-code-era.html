The Cheap Code Era.

AI will automate coding before it can own software. The cheap code era is here, but the expensive part of software is moving from syntax to systems.
PM
Pugalenthi Magendran
May 2026  ·  Melbourne, Australia
12 min read

The mistake is thinking the future of software depends on whether AI can write code.

That question is already half-obsolete.

AI can write code. It can generate components, build pages, connect APIs, create tests, explain unfamiliar repositories, refactor functions, scaffold apps, fix common bugs, and produce working prototypes from vague English. That is no longer science fiction. That is the current baseline. The real question is harder: when does AI stop being a coding assistant and become an autonomous software engineer?

That is the question that matters for jobs, startups, education, and the future shape of technical work. The answer cuts both ways. AI will automate a large share of coding sooner than most traditional engineers want to admit. It will also take longer to automate software engineering than most AI maximalists want to admit.

Coding is the act of producing code. Software engineering is the act of turning messy human intent into a system that works, survives, scales, remains secure, can be changed later, and does not create unacceptable damage when reality disagrees with the plan. Those are not the same job.

The cheap code era has already begun. The expensive part is moving elsewhere.

Key idea

AI will automate coding before it can own software. The cheap code era is here, but the expensive part of software is moving from syntax to systems, judgment, verification, security, and accountability.

I. Vibe coding is the first visible symptom

Vibe coding is not just a meme. It is the cultural name for a real shift. IBM defines vibe coding as a style of development where users express intent in plain language and AI turns that intent into executable code.1 The point is not that the human writes every line. The point is that the human steers the system through prompts, feedback, and iteration.

That sounds simple, but it changes the psychology of software. A person who could not previously build an app can now build a small tool. A founder who would have needed a freelance developer can now prototype alone. A designer can create a working interface. A student can build a dashboard. A non-technical operator can automate a workflow. The Verge described this as the rise of “personal software,” custom tools made for one person’s exact need, often with rough edges, but good enough to be useful.2

This is the first market where AI coding becomes truly transformative. It is software that was never worth hiring a developer to build: small tools, private dashboards, internal scripts, temporary apps, workflow automations, personal CRMs, one-off data cleaners, tiny interfaces wrapped around a database. Before AI, most of this software did not exist because the cost of building it was higher than the value of having it. Now the cost collapses.

AI does not only replace software labour. It creates software demand that was previously uneconomic.

The world will have much more software because the minimum viable cost of software creation is falling. But there is a trap here. Just because a thing can be generated does not mean it is engineered. Vibe coding is excellent for disposable software. It is dangerous when people confuse disposable software with durable systems.

II. The line between coding and engineering

The future makes more sense if software is split into three layers.

The first layer is disposable software: personal scripts, prototypes, landing pages, small dashboards, experimental apps, one-off automations, and tools built for a narrow purpose. If they break, the damage is low. If they get messy, they can be regenerated. If they are ugly, only one person may care. AI will dominate this layer.

The second layer is commodity production software: small business websites, CRUD apps, admin panels, booking systems, internal workflow tools, standard SaaS features, integrations, reporting dashboards, and simple mobile apps. These systems matter, but they follow known patterns. The main challenge is not inventing new computer science, it is applying familiar patterns correctly. AI will automate much of this layer, but humans will still need to define requirements, check security, choose tradeoffs, and own the result.

The third layer is durable systems: banking platforms, healthcare systems, identity systems, payment infrastructure, cloud infrastructure, developer platforms, large enterprise software, regulated AI systems, safety-critical software, and high-scale distributed systems. In this layer, mistakes compound. Security matters. Reliability matters. Legal responsibility matters. Maintenance matters. The cost of being wrong is high. AI will deeply assist this layer. It will not fully own it soon.

The confusion happens because people use one word, “coding,” for all three layers. Generating a working personal app and maintaining a secure banking system are not the same activity.

The first layer is increasingly AI-native. The second is becoming AI-assisted. The third remains human-accountable.

III. The evidence: AI coding agents are no longer toys

The strongest signal is not that chatbots can write functions. The stronger signal is that AI agents are being embedded directly into software workflows.

GitHub’s Copilot coding agent is already generally available. GitHub describes it as an asynchronous, autonomous developer agent that can be assigned a task, work in a GitHub Actions-powered environment, research the repository, create a plan, make changes on a branch, and open a pull request.3 That is the shift. AI is moving from autocomplete inside an editor to agent inside the engineering workflow.

This matters because the pull request is the unit of modern software work. Once AI can move from issue to branch to tests to PR, it is no longer merely suggesting code. It is participating in the software delivery process.

Anthropic’s Economic Index points the same direction from the usage side. Coding remains the most common use of Claude, with Computer and Mathematical tasks accounting for 35% of Claude.ai conversations in March 2026. The earlier January 2026 report also found API usage heavily concentrated in Computer and Mathematical tasks, consistent with automation-friendly workflows like code generation and data processing.4 This is not fringe behaviour. Coding is one of the first places where AI becomes economically real.

The near-term future is obvious: more agents, deeper repository context, longer-running tasks, automatic PRs, AI code review, AI test generation, AI security checks, and AI maintenance bots. But the evidence also shows why full autonomy is not here yet.

IV. The benchmark reality: impressive, not solved

SWE-bench became one of the most important benchmarks because it tests AI systems on real GitHub issues rather than isolated coding puzzles. SWE-bench Verified is a human-filtered subset of 500 problems, and the official benchmark family tracks how often AI systems resolve issues.5 The numbers on these benchmarks have improved quickly, which is why people feel the ground moving.

But there is a difference between solving a bounded GitHub issue and owning a professional software project. That is why SWE-Bench Pro matters. It was designed to test more realistic, enterprise-level software engineering work: 1,865 problems from 41 actively maintained repositories, including tasks that may take professional engineers hours to days and require multi-file changes. In the original SWE-Bench Pro paper, widely used coding models under a unified scaffold remained below 25% Pass@1, with GPT-5 achieving 23.3% at the time.6

That number should sober people up. AI systems are becoming powerful enough to matter, but not reliable enough to replace professional engineering judgment wholesale.

AI is excellent at bounded code generation. AI is improving fast at issue resolution. AI is still weak at long-horizon software ownership.

That gap is where the next decade of software work will be fought.

V. The most important curve: task horizons

If there is one research direction that matters most for forecasting autonomous coding, it is task horizon. METR introduced a useful concept: the length of task an AI agent can complete reliably, measured by how long a human expert would take to do the same task. Its 2025 research found that frontier AI task-completion horizons had been doubling roughly every seven months over the previous six years. On their software task suite, models such as Claude 3.7 Sonnet had a 50% time horizon around 50 minutes at the time of the study.7

This is the strongest argument for rapid automation. If the curve continues, AI moves from minute-long tasks to hour-long tasks, then day-long tasks, then week-long tasks. METR notes that extrapolating the trend suggests that, within under a decade, AI agents may independently complete a large fraction of software tasks that currently take humans days or weeks.7

But there is one crucial detail. 50% success is not production autonomy. A system that succeeds half the time is useful as an assistant. It is not enough for serious software ownership.

For low-risk tasks, 70% may be useful. For ordinary production work, 90% may still require review. For payments, healthcare, security, infrastructure, or safety-critical systems, even 99% may not be enough without evidence, rollback, accountability, and human signoff.

So the task-horizon curve tells us that AI capability is rising fast. It does not tell us that organisations can safely hand over responsibility.

VI. The trust tax

Every generation, technology creates a verification burden. AI-generated code is no different.

Stack Overflow’s 2025 Developer Survey found that more developers actively distrust AI tool accuracy than trust it: 46% distrust the output, 33% trust it, and only about 3% highly trust it. Experienced developers were especially cautious.8 That is the trust tax. AI can produce code quickly. But someone still has to answer: does it work, does it solve the right problem, does it fit the system, does it introduce a security flaw, does it break an edge case, can it be maintained, can it be deployed safely, can it be rolled back?

This is why AI can make individuals feel faster while making teams more complicated. Google’s DORA research shows the nuance. Its 2025 report says AI adoption among software development professionals surged to 90%, with professionals using AI in core workflows for a median of two hours per day. But DORA’s broader work also shows that the delivery system matters: faster code generation does not automatically translate into stable software delivery.9

The hidden bottleneck is not typing. It is absorption. A team can only absorb so many changes before review, testing, architecture, security, and deployment become the constraint.

In the old world, code was expensive. In the new world, code becomes cheap, but trustworthy change remains expensive.

VII. The anti-hype result nobody should ignore

The strongest reality check comes from METR’s randomised controlled trial on experienced open-source developers. The study involved 16 experienced developers working on their own mature repositories. Developers expected AI tools to make them faster. Instead, when AI tools were allowed, they took 19% longer to complete tasks. The study used real work in mature projects where developers had an average of five years of prior experience.10

This does not mean AI coding is useless. It means context matters. AI helps when the problem is standard, the task is bounded, the codebase is unfamiliar, the tests are strong, and mistakes are cheap. AI can slow things down when the developer already knows the codebase, the project has high standards, the task is subtle, and reviewing plausible-but-wrong suggestions takes longer than writing the correct change directly.

This is one of the most important distinctions in the whole debate.

AI is strongest when the cost of generation is the bottleneck. AI is weaker when the cost of judgment is the bottleneck.

Many software tasks are not bottlenecked by typing speed. They are bottlenecked by understanding. That is why the best engineers are not merely code typists. They are people who can see the system.

VIII. Security is the hard wall

Security is one of the main reasons full autonomy will lag behind code generation. AI can write code that looks correct while quietly introducing vulnerabilities. The Cloud Security Alliance warns that AI coding assistants are powerful but are not security tools, because they do not inherently understand an application’s risk model, internal standards, or threat landscape.11

Veracode’s 2025 GenAI Code Security Report found that 45% of evaluated AI-generated code samples failed security tests and introduced OWASP Top 10 vulnerabilities.12 Veracode is a vendor, so the number should be treated as one evidence point rather than universal truth, but the direction is clear: generated code needs security controls.

The deeper issue is that AI does not merely increase the amount of code. It increases the amount of code that arrives with confidence. A junior developer who is unsure asks questions. An AI system can generate insecure code with the tone of certainty. The risk is not only bad code. It is bad code that looks clean enough to pass casual review.

Autonomous coding will therefore require more than better models. It will require stronger test suites, secure coding policies, dependency controls, secrets protection, permission boundaries, automatic security scanning, code provenance, rollback systems, runtime monitoring, and human review on high-risk changes.

The future software factory is not just an AI that writes code. It is an AI surrounded by guardrails.

IX. The autonomy ladder

The question “when can AI automate coding?” only makes sense if we separate the levels.

Level 1

AI writes snippets. Already normal. Functions, components, SQL queries, scripts, tests, and explanations.

Level 2

AI edits files. Also normal. Tools can modify existing files, refactor components, update routes, change schemas, and fix obvious bugs.

Level 3

AI completes issues. Now emerging. An agent can take a GitHub issue, inspect the repo, plan a fix, edit files, run tests, and open a pull request.

Level 4

AI builds small apps. The vibe coding layer. A person describes the app, and the system creates the frontend, backend, database, deployment files, and basic UX.

Level 5

AI maintains commodity systems. Agents handle routine maintenance: dependency updates, bug fixes, tests, docs, small features, migrations, and monitoring improvements.

Level 6

AI operates engineering pipelines. Multiple agents coordinate across implementation, testing, review, security, deployment, and observability.

Level 7

AI owns durable software. The system can understand requirements, design architecture, implement changes, test deeply, secure the system, deploy safely, monitor behaviour, respond to incidents, and remain accountable over time.

Level 7 is not here yet. When it arrives technically, it may still not arrive legally or institutionally.

The pattern is clear. AI automates common software first. AI assists complex software next. AI struggles longest where mistakes are expensive, context is hidden, and accountability is unavoidable.

XI. The timeline

2026 to 2027

Personal software explodes

This is the era of vibe coding as a mass behaviour. Non-programmers and semi-technical people build tools that would never have been worth hiring for. The average quality will be messy, but the volume will be enormous. A lot of it will be private software: apps for one person, one team, one workflow, one temporary need.

This is not the death of software engineering. It is the birth of a new category: software too small to justify traditional engineering.

2027 to 2029

Agents become normal in the PR loop

AI agents become part of GitHub, IDEs, CI systems, and code review. Engineers assign tasks. Agents open pull requests. Humans review. Agents revise. Tests run. Some teams begin treating agents like junior developers with strange strengths and dangerous blind spots.

The strongest engineers become faster because they know how to break work into agent-solvable tasks. The weakest engineers become more exposed because the tasks they used to do are increasingly automated.

2029 to 2031

Commodity software becomes cheap

Small SaaS products, admin panels, dashboards, internal tools, simple mobile apps, CRUD systems, and standard integrations become dramatically cheaper to build. This will hurt low-end development agencies, generic freelancers, and junior implementers. It will also create more founders, more niche software, more internal automation, and more competition.

The bottleneck moves from “can you build it?” to “is it worth building, can you distribute it, and can users trust it?”

2031 to 2034

AI engineering teams emerge

By this stage, many teams may operate with multiple specialised agents: implementation agents, test agents, review agents, documentation agents, security agents, migration agents, observability agents. Humans become more like architects, reviewers, product owners, and incident commanders.

The best companies will not be the ones that let AI write the most code. They will be the ones that build the best system for safely absorbing AI-generated change.

2035 and beyond

Full autonomy becomes possible in places, but not universal

By the mid-2030s, AI may be capable of handling very long software tasks. But capability is not permission. Regulated industries, safety-critical software, finance, healthcare, identity, defence, infrastructure, and enterprise systems may still require human accountability.

The legal system does not care that the model seemed confident. Customers do not care that the agent had good intentions. Boards do not care that the benchmark score was high. If the system fails, someone owns the failure. That is why full software autonomy will arrive unevenly.

XII. The labour-market consequence

The biggest job impact will not be that every software engineer disappears. The biggest impact will be compression of the bottom layer.

AI attacks exactly the tasks that used to train juniors: boilerplate, simple bug fixes, tests, docs, small UI changes, integrations, scripts, first-pass implementations. Those tasks were not just work. They were apprenticeship.

There is already early labour-market evidence pointing in this direction. A Stanford Digital Economy Lab paper found that early-career workers aged 22 to 25 in AI-exposed occupations experienced a 16% relative employment decline, while experienced workers remained more stable.13 This does not prove AI alone is destroying junior software jobs. Labour markets are also affected by interest rates, overhiring, layoffs, outsourcing, and macro conditions. But it fits the pattern.

AI does not need to replace senior engineers first. It only needs to reduce the need for juniors.

The old ladder was: junior tasks, then skill, then judgment, then seniority. If junior tasks disappear, the path to seniority gets harder. This is why the future junior developer cannot just be someone who knows syntax. That layer is gone. The future junior needs to be AI-native, product-aware, good at debugging, able to read code, able to test, able to reason from first principles, and able to prove that something works. The bar rises.

XIII. What survives

The work that survives is not “coding” in the narrow sense. It is the work around code.

Understanding the problem. Choosing the architecture. Designing the data model. Defining the security boundary. Knowing the user. Deciding what not to build. Testing edge cases. Reading logs. Handling incidents. Managing tradeoffs. Knowing when the AI is wrong. Owning the outcome.

This is why the phrase “AI will replace programmers” is both true and false. It will replace many people whose value is mostly producing standard code from clear instructions. It will not quickly replace people whose value is deciding what should exist, how it should behave, and whether it is safe to trust.

The job changes from typing to directing. From implementation to specification. From writing every line to judging every consequence.

XIV. The real bottleneck is not code. It is confidence.

The cheap code era creates a paradox. More software becomes possible. But more software also means more things to maintain, secure, verify, update, monitor, and explain.

When code was expensive, scarcity filtered bad ideas. Many tools were never built because the cost was too high. When code becomes cheap, the world fills with software. Some of it will be useful. Some of it will be fragile. Some of it will be insecure. Some of it will be abandoned. Some of it will be built by people who do not understand what they have built.

The question will no longer be “who can write the code?” It will be “who can make code trustworthy?” This is why the next software era belongs to people who can combine AI fluency with engineering discipline. The winners will know how to use agents without surrendering judgment. The losers will confuse generated software with engineered software.

The final forecast

AI can already build useful personal software. By 2027, AI will be a normal way to create small tools, simple websites, prototypes, scripts, and internal automations. By 2029, AI agents will handle a large share of bounded development tickets and open useful pull requests across many repositories. By 2030, much commodity software will be mostly AI-generated: CRUD apps, admin panels, dashboards, small SaaS apps, simple mobile apps, and standard integrations. By 2032, many engineering teams will operate more like human-led agent teams, with AI doing much of the implementation, testing, documentation, and maintenance. By 2035, AI may be capable of owning large parts of serious software development, but full autonomy will remain uneven because production systems require security, reliability, legal accountability, organisational context, and trust.

So the answer is not one year. The answer is a ladder. Coding becomes automated first. Commodity software becomes cheap next. Engineering teams become agentic after that. Durable systems remain human-accountable the longest.

That is the future. Not the end of software engineering. The end of code as the moat.

The value moves from code to intent. From syntax to systems. From implementation to taste. From typing to verification. From building the thing to owning the consequences of the thing.

For seventy years, software was scarce because writing it required specialised knowledge. Now the act of writing software is becoming cheap. That does not make software worthless. It changes where the value lives. The cheap code era will create more software than the world has ever seen. But the future will not belong to the people who generate the most code. It will belong to the people who know what code should exist, what should never be built, and what must be proven before anyone trusts it.
